# Deliver to a Shipfox-hosted project

Use this procedure in place of steps 7 to 9 of `skill://shipfox/create-workflow-from-template/SKILL.md` when the selected project has a null `source_connection`. Shipfox hosts its config in a repository you write to by branch. You commit to a branch, test the branch, and stop.

1. Choose a branch such as `shipfox/add-<template>`. Call `commit_config_changes` with that branch, no `expected_head`, a short `message`, and one change: the validated YAML at `.shipfox/workflows/<descriptive name>.yml`, with the template marker. Keep setup commands inline. If the tool returns `repository-read-only`, the config lives in a linked repository: follow steps 7 to 9 of the skill instead.
2. If step 6 ended with no event for an integration trigger, do not run. Report "shape validated, not executed" and go to step 4.
3. Follow `skill://shipfox/test-workflow-change/SKILL.md`, but call `create_dev_run` with `ref` set to the branch, `commit` set to the commit the last call returned, `config_path` set to the committed file, and no `content`. Share the `run_url`; if absent, share `run_id` and say no UI link was returned. To change the file after a failed run, read it with `read_config_file` at the branch, then commit again with that commit as `expected_head`. On `stale-head`, read the files at `details.head` and retry.
4. In your final message, name the branch and share the run link. Say that the workflow is tested on the branch and is not live yet, because a person has to approve the branch before it reaches the default branch. Never suggest a pull request, and never ask the user to open one.
