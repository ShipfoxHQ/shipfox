A **job** is the unit that Shipfox places on a runner. A **step** is one ordered
action inside that job. A step is a run step, an agent step, or a tool step.

The main design choice is where one job ends and the next begins. That choice
decides which steps share a checkout, what can run at the same time, and which
results must pass from one job to another.

## Three kinds of step

Each kind of step performs a different kind of work.

| Step | Performs | Runs on |
| --- | --- | --- |
| Run step | A shell command in the job's checkout. | The runner. |
| Agent step | A goal that an agent pursues in the checkout. | The runner. |
| Tool step | One integration operation with inputs the workflow supplies. | The Shipfox API, through an integration connection. |

A tool step has no working tree. It can't read files, set `env`, or use
`secrets`. Its inputs come from run data, and its result becomes step outputs
for later steps. Shipfox makes the call, so the provider credential never
reaches the runner.

The job still holds its runner while a tool step runs. The runner waits for
the call to finish and then continues with the next step. A job made only of
tool steps still needs a runner. [Integrations, integration connections, and
tools](/understand/integrations-connections-and-tools) explains when a tool
step fits better than an agent with tools.

## What lands at the job root

Every step starts in the job root, shown as `.`. By default the root holds a
checkout of the project that owns the workflow. Each job gets its own copy.

A first step that is a checkout can replace it. When that step sets no `path`,
or sets `.` or `./`, its repository lands at the root instead, and Shipfox skips
the project checkout. When it sets any other `path`, such as `path: helm`, the
repository goes into that folder and the project checkout stays at the root.

Set `checkout: false` on the job to skip the project checkout and start with an
empty root. A later checkout step with no `path`, or with `.` or `./`, can then
fill it.

Only one checkout owns the root. Every other checkout step must set `path`, and
Shipfox rejects the workflow when one doesn't.

```yaml title=".shipfox/workflows/release.yml"
# yaml-language-server: $schema=https://www.shipfox.io/docs/workflow.schema.json
name: Release
runner: shipfox

triggers:
  manual:
    source: manual

jobs:
  release:
    steps:
      - checkout:
          repository: acme/helm
          path: helm
      - run: ls . helm
```

In this job, `.` holds the project and `helm` holds `acme/helm`.

## When to keep steps in one job

Steps in one job run in order and use the same checkout. A later step can read
files that an earlier step changed. It can also use packages that an earlier
step installed.

Steps don't share one long-lived shell process. A shell variable set in one run
step doesn't reach the next. Save a file in the checkout when the next step
needs it. Publish an output when the value must become workflow data.

One job is usually the right choice when steps must:

- Edit and check the same files.
- Reuse an expensive local setup.
- Repeat together in a feedback loop.
- Use the same runner capabilities and repository permission.

The tradeoff is less parallelism. One slow step holds the job's runner and
delays every later step.

## When to split work into jobs

Each job gets a fresh checkout. It can use a different runner or repository
permission. Jobs without dependencies can start at the same time when capacity
is free.

Separate jobs fit work that must:

- Run in parallel.
- Fail or skip on its own.
- Use a different execution environment.
- Expose a small, named result to later work.

The cost is extra setup. Two jobs that both need Node.js packages each
install them again. Their files, process environment, and logs stay separate.

This complete workflow shows the split:

```yaml title=".shipfox/workflows/check-and-review.yml"
# yaml-language-server: $schema=https://www.shipfox.io/docs/workflow.schema.json
name: Check and review a change
runner: shipfox

triggers:
  manual:
    source: manual

jobs:
  lint:
    steps:
      - run: npm ci && npm run lint

  test:
    steps:
      - run: npm ci && npm test

  review:
    needs: [lint, test]
    steps:
      - prompt: Review the repository for likely bugs and missing tests.
```

`lint` and `test` can run in parallel. Each installs its own dependencies.
`review` waits for both, but receives neither job's files nor logs. It reviews
its own fresh checkout.

The `shipfox` label selects the default hosted runner. The [Hosted runners
reference](/reference/runner-labels) lists the other sizes.

The [parallel CI
recipe](/how-to/recipes/parallel-ci-agent-review) applies this shape to a GitHub
push. The [job fields
reference](/reference/workflow-schema#job-fields) defines the dependency syntax.

## When a step or job runs

By default, a failure stops the work that follows it. A step is skipped when an
earlier step in the same job failed. A job is skipped unless every job in its
`needs` succeeded. This default protects writes: a step that pushes a branch
doesn't run after the tests before it failed.

The `run_after` field changes the default on one step or job.

| `run_after` | A step runs when | A job runs when |
| --- | --- | --- |
| `success` (default) | No earlier step in the job failed. | Every job in `needs` succeeded. |
| `failure` | An earlier step in the job failed. | At least one job in `needs` failed. |
| `always` | Whatever earlier steps did. | Whatever the status of `needs`. |

A job waits until every job in its `needs` has finished, whatever its
`run_after`. A job with `run_after: failure` looks only at the jobs it names in
`needs`, not at the jobs before those.

An `if` adds to `run_after`. It doesn't replace it. Shipfox checks `run_after`
first and evaluates the `if` only when `run_after` lets the step or job run.
Both must pass. A step with an `if` and no `run_after` is still skipped after an
earlier failure.

```yaml title=".shipfox/workflows/fix-and-report.yml"
# yaml-language-server: $schema=https://www.shipfox.io/docs/workflow.schema.json
name: Fix and report
runner: shipfox

triggers:
  manual:
    source: manual
    with:
      push: "true"

jobs:
  fix:
    checkout:
      permissions:
        contents: write
    steps:
      - key: test
        run: npm ci && npm test
      # Skipped when the test step failed, even though it has an if.
      - key: push
        if: ${{ inputs.push == "true" }}
        run: git push origin HEAD
      # Runs whether the earlier steps passed or failed.
      - key: summary
        run_after: always
        run: echo "Tests finished."

  report_failure:
    needs: [fix]
    run_after: failure
    steps:
      - run: echo "The fix job failed."
```

Use `failure` for a handler that only makes sense after something broke, such
as a failure report. Use `always` for work that must happen either way, such as
a summary or a cleanup. With `always`, the `if` can still read a status to
choose between the two cases.

A step or job that runs after a failure can read values that were never set. A
skipped step reports no outputs. Guard an optional output with `has()`, as in
`has(steps.test.outputs.report)`, before a condition reads it.

When `run_after` skips a step or a job, the run page says so and shows the
check that rejected it. A workflow synced before `run_after` existed keeps its
earlier behavior until its file next changes: an `if` on such a step or job
still replaces the default.

The [step fields](/reference/workflow-schema#step-fields) and [job
fields](/reference/workflow-schema#job-fields) references define the field.

## How results move between jobs

A job output passes a small value to later jobs. It fits a version, a decision,
an identifier, or a URL.

An artifact is a file or a directory. One job's checkout isn't available to
another job. Put large reports and build products in an external store. Pass
only their location as an output.

This explicit hand-off means a later job can't depend on a file that another
job left behind by accident. It also makes reruns and runner placement easier
to predict.

A named [agent session](/understand/agent-sessions) is a third way to pass
context. It gives one agent's conversation to a later agent step in the same
run. It doesn't pass files either.

## A job also chooses its runner and its access

A job selects its runner labels as a whole. Split work when one part needs a
private network, special hardware, or another operating system. Keep it
together when every step needs the same environment.

Repository checkout permission also applies to the whole job. Each agent step
selects its own integration tools, and each tool step names one operation.
Both are separate from Git access. This matters when an agent reads code but
only one later step must write to an external system.

[Runners and execution
environments](/understand/runners-and-execution-environments) explains
placement. [Agent access](/integrations/github/guides/read-pull-request) shows
the separate repository and integration controls. [Call an integration
tool](/how-to/author-workflows/call-integration-tool) shows a tool step.

## Retries and later events stay inside the job

A feedback loop repeats steps inside one job execution, so the repeated work
keeps the same checkout. A listening job creates a new job execution for each
later event or event batch. It can run its steps several times in one run.

Choose the job boundary before you add either kind of repetition. A job that
mixes unrelated writes makes retries and later events harder to handle safely.
