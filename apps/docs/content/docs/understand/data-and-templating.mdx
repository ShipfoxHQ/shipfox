**Context** is the data a workflow can read while it runs. It starts with the
event or the manual inputs. It grows as jobs and steps produce results.

## How interpolation works

Interpolation reads a value from context and inserts it into a workflow field.
Wrap the expression in `${{ }}`. For example, `Hello ${{ inputs.name }}` adds
the `name` input after `Hello`.

Use interpolation to add data to text or settings. It does not decide whether
work runs.

A predicate is a yes-or-no check. For example, `step.exit_code == 0` passes a
gate when the command succeeds. Filters, conditions, gates, and job success
rules use predicates.

The [Expressions reference](/reference/expressions) defines the exact syntax
and available fields.

## When data becomes available

A workflow gains data as the run progresses:

- Run details, trigger data, inputs, and variables are available from the start.
- Step outputs become available after the step finishes.
- Job outputs become available after an upstream job finishes.
- Restart feedback becomes available when a gate repeats steps.

The [Contexts reference](/reference/contexts#context-availability) lists the
exact availability of these values, tool results, listening events, and secrets.

## How outputs move results between jobs

Steps in one job can share files, but files don't cross a job boundary. An
output turns a result into named workflow data that later work can read.

This complete workflow moves a version between two isolated jobs:

```yaml title=".shipfox/workflows/pass-version-between-jobs.yml"
# yaml-language-server: $schema=https://www.shipfox.io/docs/workflow.schema.json
name: Pass a version between jobs
runner: shipfox

triggers:
  manual:
    source: manual

jobs:
  package:
    steps:
      # Takes the output from what the command prints.
      - key: read_version
        run: git describe --tags --always
        outputs:
          version:
            type: string
            from_stdout: true
        # Publishes every output of this step as an output of the job.
        export: true
      # Writes name=value lines to a file, so one step creates several outputs.
      - key: read_commit
        run: |
          echo "sha=$(git rev-parse HEAD)" >> "$SHIPFOX_OUTPUT"
          echo "branch=$(git branch --show-current)" >> "$SHIPFOX_OUTPUT"
        outputs:
          sha: string
          branch: string
        export: true

  publish:
    # Waits for the package job and makes its outputs readable.
    needs: package
    steps:
      # Reads the job outputs.
      - run: printf 'Publishing version %s\n' "${{ jobs.package.outputs.version }}"
      - run: printf 'Built from commit %s\n' "${{ jobs.package.outputs.sha }}"
```

A step creates an output in one of two ways. The `read_version` step takes
`version` from what its command prints. The `read_commit` step writes
`name=value` lines to the file `$SHIPFOX_OUTPUT`, which lets one step create
several outputs.

`export` publishes the outputs of both steps as outputs of the `package` job.
The `publish` job declares the dependency and puts the values in its commands.

### Rename or join values

`export` keeps the name of the step output. Sometimes a job output needs a
different name. Sometimes it needs a value that joins several step outputs. In
these cases, add an `outputs` map to the job. Each line of the map gives one
name and the expression that makes its value.

This map belongs to the `package` job. It joins the version and the commit:

```yaml
outputs:
  release: ${{ steps.read_version.outputs.version }}+${{ steps.read_commit.outputs.sha }}
```

A later job reads this value as `jobs.package.outputs.release`.

### Pass a list or an object

An output can hold a list or an object. Declare this output with the type
`json`.

A later job can then read one part of the value. For example,
`jobs.review.outputs.findings[0].severity` reads the `severity` field of the
first finding.

A job output keeps the list or the object in two cases:

- The step exports the output.
- A line of the job `outputs` map contains one expression and no other text.

If a line of the map mixes text and expressions, the job output is text. A
later job can't read one part of it.

Interpolation writes a list or a map as JSON text. To pass one to a shell
command, put it in `env` and parse the environment variable. You don't need to
call `toJson()` first.

### When an output is the wrong tool

Outputs fit small facts. Files and build products belong in external artifact
storage, with an output that carries their location. [Step
outputs](/reference/workflow-schema#step-outputs) defines declaration types and
encoding. [Job outputs](/reference/limits#job-outputs) lists the limits for job
outputs.

Sometimes the steps of one job must share a tool or an environment variable.
You don't need an output for this. A step can give an environment variable or
a `PATH` directory to the steps that run after it in the same job. See [Share
tools between steps](/how-to/author-workflows/share-tools-between-steps).

## Treat outside data as text, not as instructions

Events, inputs, and step outputs carry data that the workflow didn't write. A
shell step reads that data as text, so it can't run as a command. [A few shell
constructs](/reference/workflow-schema#run-step-fields) read their own arguments
again and break that protection.

Nothing protects a prompt or a job setting this way. An event can contain
instructions for an agent. It can also choose the runner a job uses. Keep event
data out of any choice you wouldn't let a stranger make.

A secret follows the same rule. Only a run step's command or `env` can bind one,
so no prompt, model field, or predicate can read it. Shipfox never resolves the
value on the server. The runner pulls it before the step starts and masks it
in logs, outputs, and error messages. Masking is a safety net, not a
guarantee, so a step that transforms and prints a secret can still leak it.
[Integrations, integration connections, and
tools](/understand/integrations-connections-and-tools) explains the external
credential boundary.
