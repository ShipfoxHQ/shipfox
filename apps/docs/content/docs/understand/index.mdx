A **workflow** describes engineering work that Shipfox runs for a team. It
combines agent instructions, commands, and checks in a YAML file stored in the
repository. Shipfox orchestrates that work and records each run.

Consider a workflow that investigates a new error and proposes a fix. The
example below follows the work from the alert to human review.

## An event starts the work

A monitoring tool reports a new error. A **trigger** in the workflow matches
that event and starts a **run**, the record of this particular investigation.

The run uses a snapshot of the workflow. Later edits to the workflow do not
change work already in progress. [Events and triggers](/understand/events-and-triggers)
explain how a team chooses which signals start work.

## Agents and commands work on the code

A **job** groups the steps for the investigation. A **runner** checks out the
repository and executes those steps in order. Each job has its own checkout;
steps within that job share it.

An agent step investigates the error and proposes a change. A command step
runs the tests that the team chose. Agents handle work that needs judgment;
commands perform explicit operations, such as running a test suite.

[Jobs and steps](/understand/jobs-and-steps) explain how to divide work.
[Agent access](/understand/integrations-connections-and-tools) explains how a
workflow grants tools to each agent step.

## Checks decide whether work continues

If the tests fail, a **feedback loop** can return the failure evidence to the
agent for another attempt. The loop stops when the check passes or the attempt
limit runs out. Passing tests establish what those tests cover, rather than
guaranteeing that the whole change is correct.

In this example, the workflow opens a pull request only after the tests pass.
An engineer reviews the change and decides whether to merge it.

## Later feedback can continue the work

A **listening job** keeps a run open for related events, such as review
comments on its pull request. That lets a workflow respond to feedback after
the initial result is ready.

Feedback loops and listening jobs solve different problems. A failed check
means the current work needs another attempt. A review comment supplies new
input. Each needs its own stopping rules.

## The dashboard records what happened

The run view shows the jobs, steps, agent messages, tool calls, and cost.
Failures remain visible alongside the evidence needed to investigate them.
The team can compare the intended workflow with the work that actually ran.
