A **feedback loop** repeats part of a job after a check rejects the result. One
step does the open-ended work. A later step measures it. The job returns to the
earlier step only when the check fails.

A **gate** is the decision point, not the loop itself. A gate can accept or
reject a result without repeating anything. The restart rule creates the loop.

## Gate outcomes

The check answers one question: is this result good enough to continue? The
restart answers another: which earlier work gets another attempt?

Because the two are separate, a workflow can:

- Fail the job without retrying unsafe work.
- Restart only the part that can improve the result.
- Give the repeated step evidence from the failed check.

This also makes the run readable. The check result explains why the job
continued, failed, or created another step attempt.

## Use an independent check, not the agent's opinion

An agent that judges its own work repeats the same judgment. A test, a type
check, a linter, a policy script, or an independent review measures something
outside that judgment.

The check doesn't need to prove every property. It must prove the property that
decides whether the next action is safe. A unit test can guard behavior before
a commit. A policy check can guard a deploy. A read-back can confirm an
external write.

This complete workflow shows the loop. The project needs an `npm test` command
and configured agent defaults.

```yaml title=".shipfox/workflows/fix-tests.yml"
# yaml-language-server: $schema=https://www.shipfox.io/docs/workflow.schema.json
name: Fix failing tests
runner: shipfox

triggers:
  manual:
    source: manual

jobs:
  fix:
    steps:
      - key: fix
        prompt: >
          Fix the failing tests in this repository.
          ${{ !has(step.restart)
            ? "Run the tests and inspect the failures."
            : has(step.restart.from.log_path)
              ? "The tests still fail. Read their log at " + step.restart.from.log_path + " and fix the cause."
              : step.restart.feedback }}

      - key: test
        run: npm test
        gate:
          success: step.exit_code == 0
          on_failure:
            restart_from: fix
            feedback: The tests still fail. Reproduce the failure and fix its cause.
```

The first attempt gets initial guidance. A failed test restarts `fix` in the
same job checkout, so the agent can revise its files. The agent reads the
failed test log, or the gate feedback when there is no log. A passing test lets
the job continue.

The [Gate fields
reference](/reference/workflow-schema#gate-fields) defines the exact fields.

## Route several loops by their checking step

One job execution can contain several feedback loops. Shipfox records which
checking step caused a restart. The workflow can identify the relevant loop
and run its matching recovery step.

[Build a feedback
loop](/how-to/recipes/build-feedback-loop) shows a complete two-loop
workflow and how to route each failure.

## Give the next attempt useful feedback

A retry without new evidence can repeat the same mistake. The repeated step
needs to know which property failed and why. Two kinds of evidence answer that:
the gate feedback and the log of the failed check.

Feedback isn't a new event. It belongs to the restart decision, and only the
repeated attempt can read it. [Context and
templating](/understand/data-and-templating) explains when each kind of data
becomes available.

## Give the next attempt the failed log

The output of the failed check usually explains the failure better than a
fixed feedback message. Shipfox keeps a copy of each step attempt's log on the
runner, so the workflow doesn't need to capture it. `step.restart.from.log_path`
is the path to the log of the failed check. The repeated step passes the path
to an agent or a script, which reads what it needs from the file.

The file holds the attempt's output as plain text:

- Standard output and standard error appear in the order they arrived, with the
  lines Shipfox adds, such as the exit code. Lines have no timestamps.
- Secrets are masked, as they are on the run page.
- A long log keeps only its end, where failures usually appear. The file then
  starts with a `[shipfox] Log truncated:` line. [Limits](/reference/limits#logs)
  gives the size.
- The file exists until the job execution ends. Later steps of that execution
  can read it, including after gate restarts.
- Other jobs, other runs, and `tool` steps can't read it.

`log_path` is sometimes absent, even after a failure. For example, a step that
fails before it starts its command has no log. Guard the field with `has()` and
give the next attempt another source of evidence, such as the gate feedback:

```text
has(step.restart.from.log_path)
  ? "Read the failed log at " + step.restart.from.log_path + "."
  : step.restart.feedback
```

The [Contexts reference](/reference/contexts#context-properties) lists when the
field is absent and the steps that have one.

A log is untrusted input, like any step output. Test names, dependency output,
and pull request titles can contain text that reads like an instruction. Tell
the agent to treat the log as data, and give it only the tools the fix needs.

Gate feedback stays useful next to the log. It can name the failed property in
plain words or carry values from the step's outputs.

## Loop bounds

Every attempt costs runner time and, for an agent, model cost. Slow checks
multiply that cost. A loop therefore needs a clear stopping rule and a limited
number of attempts.

The loop stops in one of two states:

- The check passes.
- The attempt limit runs out and the job fails.

[Limits](/reference/limits) lists the exact attempt limits. The [run
history](/understand/workflows-and-runs) keeps each step attempt and its
feedback.

## Keep external writes out of the loop

A restart repeats every step from the restart point through the gate. A
deploy, a notification, a comment, a payment, or a repository push inside that
range can happen more than once.

Prefer this order:

1. Make local or reversible changes.
2. Run the check.
3. Perform the external write only after the gate passes.

When a write must happen inside the repeated range, make it safe to repeat. Use
a stable identity, and update or read back the existing result instead of
creating a new one on every attempt.

A failed log helps an agent fix the cause of a failed write. It doesn't make
the write safe to run again. A push step that failed after it created a branch
or a commit finds them on the next attempt, and its script must accept them.
[Turn a Sentry issue into a verified pull
request](/how-to/recipes/event-to-verified-pull-request) shows a push step that
is safe to run again.

A loop can repeat a bad side effect as easily as it can improve code. Don't use
it to retry a deploy or an external write that has no check in front of it.

Use the linked authoring guide to add this pattern to a workflow.
