A **feedback loop** runs part of a job again when a check fails. For example,
an agent step changes the code. A later step runs the tests. If the tests fail,
the job goes back to the agent step.

## How a loop runs

This complete workflow shows a loop. The project needs an `npm test` command and
default agent settings.

```yaml title=".shipfox/workflows/fix-tests.yml"
# yaml-language-server: $schema=https://www.shipfox.io/docs/workflow.schema.json
name: Fix failing tests
runner: shipfox

triggers:
  manual:
    source: manual

jobs:
  fix:
    steps:
      - key: fix
        prompt: Fix the failing tests in this repository.

      - key: test
        run: npm test
        gate:
          success: step.exit_code == 0
          on_failure:
            restart_from: fix
```

This is what happens:

1. The `fix` step runs. The agent changes the code.
2. The `test` step runs `npm test`.
3. If the tests fail, the job goes back to the `fix` step. The files that the
   agent changed are still there, so the agent can continue from them.
4. The `fix` and `test` steps run again.
5. When the tests pass, the job continues.

The [Gate fields reference](/reference/workflow-schema#gate-fields) lists the
exact fields.

## Check and restart are separate

A gate has two parts. You write each part separately:

- `success` is the check. It decides if the step passed.
- `on_failure` is the restart rule. It names the step that runs again when the
  check fails.

Because the two parts are separate, you can choose what a failed check does:

- **Stop the job.** Write only `success`. Do this when it is not safe to run
  the steps again.
- **Go back to the step that can fix the problem.** Add `on_failure` and name
  that step. The job does not start again from its first step.

## Use a separate check

Do not ask the agent that did the work to also check the work. An agent that
made a mistake often does not see that mistake when it checks.

Use a check that gives the same answer for the same code, whatever the agent
says. Good checks are:

- A test command.
- A type check.
- A linter.
- A review by a different agent step.

## Route several loops by their checking step

One job can contain more than one feedback loop. In this example, the job has
two checks, `test` and `lint`. Each check has its own fix step:

```yaml
steps:
  - key: fix_tests
    if: '${{ has(step.restart) && has(step.restart.from.key) && step.restart.from.key == "test" }}'
    prompt: Fix the failing tests.

  - key: test
    run: npm test
    gate:
      success: step.exit_code == 0
      on_failure:
        restart_from: fix_tests

  - key: fix_lint
    if: '${{ has(step.restart) && has(step.restart.from.key) && step.restart.from.key == "lint" }}'
    prompt: Fix the lint errors.

  - key: lint
    run: npm run lint
    gate:
      success: step.exit_code == 0
      on_failure:
        restart_from: fix_lint
```

`step.restart.from.key` is the key of the check that failed. Each fix step
tests this value in its `if` condition. The two `has()` tests make sure that
the value exists before the condition reads it:

- When `test` fails, the job goes back to `fix_tests`. `fix_tests` runs.
- When `lint` fails, the job goes back to `fix_lint`. `fix_lint` runs.
- On the first attempt, no check has failed. Both fix steps are skipped.

[Build a feedback loop](/how-to/recipes/build-feedback-loop) shows the complete
workflow.

## Tell the next attempt what failed

If a step runs again with the same instructions, it can make the same mistake
again. Tell the step what failed. The gate gives the restarted step two things:

- `step.restart.from.log_path` is the path of a file on the runner. The file
  holds the log of the check that failed. Shipfox saves this file for you.
- `step.restart.feedback` is the message that you write in `feedback`.

Put the path of the log in the prompt of the restarted step, and the agent
reads the file. Use the feedback message when there is no log:

```yaml
steps:
  - key: fix
    prompt: >
      Fix the failing tests.
      ${{ !has(step.restart)
        ? ""
        : has(step.restart.from.log_path)
          ? "Read the test log at " + step.restart.from.log_path + "."
          : step.restart.feedback }}

  - key: test
    run: npm test
    gate:
      success: step.exit_code == 0
      on_failure:
        restart_from: fix
        feedback: The tests still fail. Run them, read the errors, and fix the cause.
```

The prompt for `fix` has three cases:

- On the first attempt, no check has failed. The prompt adds nothing.
- After `test` fails, the prompt gives the path of the test log.
- If the failed check has no log, the prompt gives the feedback message.

The log does not always exist. For example, a step that fails before it starts
its command has no log. Always test `log_path` with `has()` before you read
it, as the example does.

The file is plain text, and secrets are masked. A long log keeps only its end.
The [Contexts reference](/reference/contexts#context-properties) and
[Limits](/reference/limits#logs) list the exact rules.

## Loop bounds

Two limits stop a loop that does not pass its check:

```yaml title=".shipfox/workflows/fix-tests.yml"
# yaml-language-server: $schema=https://www.shipfox.io/docs/workflow.schema.json
name: Fix failing tests
runner: shipfox

triggers:
  manual:
    source: manual

jobs:
  fix:
    execution_timeout: "30m"
    steps:
      - key: fix
        prompt: Fix the failing tests.

      - key: test
        run: npm test
        gate:
          success: step.exit_code == 0
          on_failure:
            restart_from: fix
            max_attempts: 8
```

- `max_attempts` is the number of times the `test` step can run. The first run
  counts. Here, if `test` fails 8 times, the job fails with
  `restart_exhausted`. The default is 5. You cannot remove the limit.
- `execution_timeout` is the time that the job can run. The time includes every
  attempt. Here, if the job is not complete after 30 minutes, it fails with
  `timed_out`.

The limit that the job reaches first stops the loop.

[Limits](/reference/limits) lists the exact values.

## Avoid repeated writes

When a gate fails, the job runs again every step from the `restart_from` step
to the step with the gate. A step in that range that pushes, deploys, or
comments does it again on each attempt.

Put such a step after the gate. It then runs one time, after the check passes:

```yaml
steps:
  - key: fix
    prompt: Fix the failing tests.

  - key: test
    run: npm test
    gate:
      success: step.exit_code == 0
      on_failure:
        restart_from: fix

  - key: push
    run: git push origin HEAD
```

Here, a restart runs `fix` and `test` again. `push` is after the gate, so it
runs only when `test` passes.

If a step that writes must stay in the loop, make it safe to run again. For
example, a push step must use the branch that an earlier attempt created, and
not fail because the branch exists. [Turn a Sentry issue into a verified pull
request](/how-to/recipes/event-to-verified-pull-request) shows a push step that
does this.

loop](/how-to/recipes/build-feedback-loop).
