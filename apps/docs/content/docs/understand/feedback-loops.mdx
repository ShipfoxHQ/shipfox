A **feedback loop** runs part of a job again when a check fails. For example,
an agent step changes the code. A later step runs the tests. If the tests fail,
the job goes back to the agent step.

A **gate** decides if a step passed. If the gate fails and has no restart rule,
the job fails. If it has a restart rule, the job goes back to an earlier step.
The restart rule creates the loop.

## Check and restart are separate

The gate checks the result. The restart rule chooses the step that runs again.
You set them separately. This lets a workflow:

- Stop the job when the check fails. Do this when a retry isn't safe.
- Restart from the step that can fix the problem, not from the start of the
  job.
- Give the restarted step the gate feedback and the log of the failed check.

The run shows the result of each gate. The result explains why the job
continued, failed, or ran a step again.

## Use a separate check

An agent that checks its own work often repeats its own mistakes. Use a check
that doesn't depend on the agent, such as tests, a type check, a linter, or a
separate review.

The check doesn't need to test everything. It must test what makes the next
step safe. For example:

- Run unit tests before a commit.
- Run a policy check before a deploy.
- Read the result of an external change to confirm it worked.

This complete workflow shows a loop. The project needs an `npm test` command and
default agent settings.

```yaml title=".shipfox/workflows/fix-tests.yml"
# yaml-language-server: $schema=https://www.shipfox.io/docs/workflow.schema.json
name: Fix failing tests
runner: shipfox

triggers:
  manual:
    source: manual

jobs:
  fix:
    steps:
      - key: fix
        prompt: >
          Fix the failing tests in this repository.
          ${{ !has(step.restart)
            ? "Run the tests and inspect the failures."
            : has(step.restart.from.log_path)
              ? "The tests still fail. Read their log at " + step.restart.from.log_path + " and fix the cause."
              : step.restart.feedback }}

      - key: test
        run: npm test
        gate:
          success: step.exit_code == 0
          on_failure:
            restart_from: fix
            feedback: The tests still fail. Reproduce the failure and fix its cause.
```

The first attempt gets initial guidance. A failed test restarts `fix` in the
same job checkout, so the agent can revise its files. The agent reads the
failed test log, or the gate feedback when there is no log. A passing test lets
the job continue.

The [Gate fields
reference](/reference/workflow-schema#gate-fields) defines the exact fields.

## Route several loops by their checking step

One job execution can contain several feedback loops. Shipfox records which
checking step caused a restart. The workflow can identify the relevant loop
and run its matching recovery step.

[Build a feedback
loop](/how-to/recipes/build-feedback-loop) shows a complete two-loop
workflow and how to route each failure.

## Give the next attempt useful feedback

A step that runs again with no new information can make the same mistake. It
needs to know what failed and why. Two sources give this information: the gate
feedback and the log of the failed check.

Gate feedback doesn't start a new run. Shipfox gives the feedback to the steps
that run after the restart. [Context and
templating](/understand/data-and-templating) shows when each type of data is
available.

## Give the next attempt the failed log

The output of the failed check usually explains the failure better than a
fixed feedback message. Shipfox keeps a copy of each step attempt's log on the
runner, so the workflow doesn't need to capture it. `step.restart.from.log_path`
is the path to the log of the failed check. The repeated step passes the path
to an agent or a script, which reads what it needs from the file.

The file holds the attempt's output as plain text:

- Standard output and standard error appear in the order they arrived, with the
  lines Shipfox adds, such as the exit code. Lines have no timestamps.
- Secrets are masked, as they are on the run page.
- A long log keeps only its end, where failures usually appear. The file then
  starts with a `[shipfox] Log truncated:` line. [Limits](/reference/limits#logs)
  gives the size.
- The file exists until the job execution ends. Later steps of that execution
  can read it, including after gate restarts.
- Other jobs, other runs, and `tool` steps can't read it.

`log_path` is sometimes absent, even after a failure. For example, a step that
fails before it starts its command has no log. Guard the field with `has()`.
When the log is absent, give the next attempt the gate feedback instead:

```text
has(step.restart.from.log_path)
  ? "Read the failed log at " + step.restart.from.log_path + "."
  : step.restart.feedback
```

The [Contexts reference](/reference/contexts#context-properties) lists when the
field is absent and the steps that have one.

## Loop bounds

Every attempt costs runner time and, for an agent, model cost. Slow checks
multiply that cost. A loop therefore needs a clear stopping rule and a limited
number of attempts.

The loop stops in one of two states:

- The check passes.
- The attempt limit runs out and the job fails.

[Limits](/reference/limits) lists the exact attempt limits. The [run
history](/understand/workflows-and-runs) keeps each step attempt and its
feedback.

## Avoid repeated writes

A restart runs every step again, from the restart step to the gate. Some steps
change things outside the job, such as a deploy, a comment, or a push. These
changes can happen more than once.

Put these steps after the gate, so they run only when the check passes.

If a step like this can still run more than once, make it safe to run again.
It should find the result of the earlier attempt and reuse it.

For example, a push step can fail after it creates a branch and a commit. On
the next attempt, the branch and the commit already exist. The push script must
use them instead of failing. [Turn a Sentry issue into a verified pull
request](/how-to/recipes/event-to-verified-pull-request) shows a push step that
does this.

To add a feedback loop to a workflow, see [Build an agent feedback
loop](/how-to/recipes/build-feedback-loop).
