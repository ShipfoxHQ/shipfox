An **integration** connects Shipfox to a tool your team already uses, such as
GitHub, Sentry, or Slack. An **integration connection** is one account or
source you connected, for example your company's GitHub organization.

An integration connection can do two things for you. Most tools do both, and
some do only one:

- **It starts workflows.** When something happens in the tool, such as a new
  issue or a new pull request, a workflow can start.
- **It gives agents and workflows access to the tool.** A step can read data
  from the tool or make a change in it, such as commenting on an issue.

```text
GitHub (acme)                                   Your workflow
      |                                               |
      |  event: a pull request was opened  ---------> |  starts
      |                                               |
      | <--------- tool: comment on the pull request  |  a step acts
      |                                               |
```

You decide what each workflow can do. A workflow names the account it uses and
the actions it needs. Nothing else is allowed. You can connect the same tool
more than once, for example one GitHub organization per team.

## Start workflows from events

Each integration connection has a short name, called its slug, such as
`github_acme`. A workflow uses that slug to say which account it listens to.

```yaml
triggers:
  on_push:
    source: github_acme # The slug of the integration connection.
    event: push
```

The slug matters when you connect the same tool twice. Two GitHub
organizations both send a `push` event. The slug tells Shipfox which one you
mean, so a workflow never reacts to the wrong account.

```text
github_acme       push  ----->  deploys the main product
github_acme_labs  push  ----->  nothing: no workflow listens to this slug
```

[Events and triggers](/understand/events-and-triggers) explains how a workflow
chooses its events. [Set up work](/how-to/set-up-work) explains how to connect
a tool.

## Give agents and workflows access to tools

A workflow can use a tool in two ways.

<Tabs items={['Tool step', 'Agent step']}>
  <Tab value="Tool step">

    You name one action and its values. Shipfox makes exactly that call. Use
    it when you already know the exact action.

    ```yaml
    steps:
      - key: notify
        tool: send_message        # One action.
        connection: slack_acme    # On this account.
        with:                     # With these values.
          channel_id: C0ABC12345
          message: "Run #${{ run.number }} started."
    ```

  </Tab>
  <Tab value="Agent step">

    You give the agent a set of tools. The agent decides when to use them and
    with which values. Use it when the work needs judgment.

    ```yaml
    steps:
      - key: review
        prompt: Review this pull request and report the two biggest risks.
        integrations:
          - include: [pull_request_read]   # Read tools only.
    ```

  </Tab>
</Tabs>

Each permission is a separate choice. An event that starts a workflow gives it
no access to the tool. Read access gives no write access. An agent can only
make changes in a tool when the workflow says so. Reading and editing the code
is not a tool either: it comes from the job's checkout, which
[Jobs and steps](/understand/jobs-and-steps#what-lands-at-the-job-root)
explains.

This keeps the first steps of a workflow safe. In the example below, a new
Sentry issue starts an agent that works on your code with no integration
tools. A later step, after the tests pass, gets one permission on GitHub: open
a pull request.

```yaml
# yaml-language-server: $schema=https://www.shipfox.io/docs/workflow.schema.json
name: Fix a Sentry issue
runner: shipfox

triggers:
  on_issue:
    source: sentry_acme          # Sentry starts the workflow.
    event: issue.created         # That gives no access to Sentry or GitHub.

jobs:
  fix:
    steps:
      - key: fix
        prompt: Find the cause of the issue and fix it.
        # No integrations: this agent can only read and edit the code.

      - key: test
        run: npm test            # A check between the fix and the change.

      - key: open_pr
        prompt: Open a pull request with the fix.
        integrations:
          - include: [create_pull_request]   # One action.
            allow_write: true                # Named as a change, on purpose.
```

Use [Call an integration tool](/how-to/author-workflows/call-integration-tool)
for a tool step and [Give an agent read-only GitHub tools](/integrations/github/guides/read-pull-request)
for an agent with tools. The [tool step fields](/reference/workflow-schema#tool-step-fields)
and [agent integration fields](/reference/workflow-schema#agent-integration-fields)
list the exact settings.

## Which repositories a workflow can reach

Two settings decide this, one on each side.

```text
All repositories in your GitHub organization
`-- Repositories the Shipfox app can see        <- you choose this on GitHub
    `-- Repositories a workflow can name         <- you choose this in Shipfox
```

- **On GitHub**, you choose which repositories the Shipfox app can see when
  you install it. Shipfox can never reach a repository outside that list.
- **In Shipfox**, each integration connection has an access mode. A new
  integration connection can reach every repository the app can see. You can
  narrow it to the repositories your projects use.

A project with [managed config](/understand/configuration#in-your-repository-or-managed-by-shipfox) has no repository
of its own. Its jobs check out only the repositories they name.

[Manage GitHub repository access](/integrations/github/guides/manage-repository-access)
explains how to change both settings. The
[GitHub tool catalog](/integrations/github/tools) says which tools the access
mode can and can't check.
