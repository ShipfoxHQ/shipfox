Use `$SHIPFOX_ENV` and `$SHIPFOX_PATH` when one step installs a tool or computes
a setting that later steps of the same job need. Each step starts a new
process, so a shell `export` or a changed `PATH` ends with the step that made
it. Shipfox reads these two files after a step and applies them to the steps
that follow.

The example below installs Nix in one step and uses it in the next. To share
another tool, keep the two `echo` lines and change the directory, the variable,
and the commands.

## Add a directory and a variable for later steps

This is a complete workflow:

```yaml
# yaml-language-server: $schema=https://www.shipfox.io/docs/workflow.schema.json
name: Share tools between steps
runner: shipfox

triggers:
  manual:
    source: manual

jobs:
  test:
    steps:
      - name: Install Nix
        run: |
          curl -L https://nixos.org/nix/install | sh -s -- --no-daemon
          echo "$HOME/.nix-profile/bin" >> "$SHIPFOX_PATH"
          echo "NIX_PATH=nixpkgs=channel:nixos-24.05" >> "$SHIPFOX_ENV"
      - run: nix develop --command make test
```

To share anything between steps, you need two things:

1. **Add a directory to `PATH`.** Write the directory to the file
   `$SHIPFOX_PATH`, one directory per line. Later steps find the commands in
   that directory.
2. **Set an environment variable.** Write `NAME=value` to the file
   `$SHIPFOX_ENV`, one variable per line. Later steps read `$NAME`.

Later run steps and action steps of the same job get the values. So do the
shell commands that an agent step runs. The step that writes the files doesn't
get them, and other jobs don't either.

Shipfox reads the files when the step exits, even if the step fails. A step
fails when `$SHIPFOX_ENV` sets `PATH` or a name that starts with `SHIPFOX_`.

<Callout title="Values in $SHIPFOX_ENV are not masked" type="warn">
  Shipfox masks only the secrets it stores. A token that a command fetches and
  writes to `$SHIPFOX_ENV` appears in the logs of any later step that prints
  it. Store the token as a [secret](/how-to/set-up-work/secrets-and-variables)
  instead.
</Callout>

## Write the files from an action

An action step gets the same two files. Append to them from the action code:

```ts
import {appendFileSync} from 'node:fs';
import {join} from 'node:path';
import {defineAction} from '@shipfox/actions';

export default defineAction(() => {
  const workspace = process.env.SHIPFOX_WORKSPACE ?? '';
  appendFileSync(process.env.SHIPFOX_ENV ?? '', 'RELEASE_CHANNEL=beta\n');
  appendFileSync(process.env.SHIPFOX_PATH ?? '', `${join(workspace, 'tools/bin')}\n`);
});
```

## Check which value a step gets

A step can receive the same variable from several places. Shipfox applies them
in this order, and a later entry replaces an earlier one:

1. The environment of the runner.
2. The values that earlier steps wrote to `$SHIPFOX_ENV`. When two steps write
   the same name, the later step wins.
3. The `env` of the workflow, the job, and the step, including the secrets they
   bind.
4. The variables that Shipfox sets, such as `SHIPFOX_RUN_ID`.

Directories from `$SHIPFOX_PATH` go in front of the existing `PATH`. The
directory written last comes first.

## Expect fresh values after a gate restart

When a [gate](/understand/feedback-loops) restarts earlier steps, later steps
get the values from the latest pass only:

- A step that runs again replaces everything it wrote in the earlier pass.
- A step that the new pass skips contributes nothing. Its earlier values and
  directories are removed.
- A step before the restart point keeps its values.

## Adapt it to your workflow

| To... | Change this |
| --- | --- |
| Share a value that has several lines | Write a `NAME<<DELIMITER` line, the value, then a line with only the delimiter. The format is the same as for `$SHIPFOX_OUTPUT`. |
| Add a directory inside the repository | Write a relative path to `$SHIPFOX_PATH`. Shipfox resolves it against the working directory of the step. |
| Use another value in one step only | Set the variable in the `env` of that step. See [Environment variables](/reference/workflow-schema#environment-variables). |
| Send a value to another job | Use an output. See [Pass values between jobs](/how-to/author-workflows/pass-outputs). |
| Use a credential | Bind a secret in `env` instead of writing it to `$SHIPFOX_ENV`. See [Add secrets and variables](/how-to/set-up-work/secrets-and-variables). |
