<Callout type="warn" title="Filter out your own runs">
  Shipfox doesn't stop a workflow from triggering itself. Filter on
  `event.project.name` and `event.run.origin`, and exclude the workflow's own
  path. See [Avoid trigger
  loops](/how-to/author-workflows/run-after-another-workflow#avoid-trigger-loops).
</Callout>

Reruns and dev runs send these events too. Filter on `event.run.attempt == 1`
to skip reruns, or on `event.run.origin == 'synced'` to skip dev runs.

## When events fire

Each run attempt sends its own `run.requested`, `run.started`, and
`run.completed` events. A job that a rerun keeps from the previous attempt
sends no job events in the new attempt.

A job sends `job.queued` and `job.started` for each of its executions, and
`job.completed` once. A one-shot job has one execution. A listening job starts
one execution for each matching event or event batch, so it sends `job.queued`
and `job.started` many times in one run. Read `event.job.execution.sequence` to
tell its executions apart. The listening job sends `job.completed` once, when
it resolves.

A skipped job sends only `job.completed`, with `event.job.status` set to
`skipped`.

**Settings → Events** lists a Shipfox event only when a workflow was listening
for it. Runs that ended before you added the trigger have no event to inspect or
replay.
